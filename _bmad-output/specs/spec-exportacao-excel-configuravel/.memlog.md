- (direction) Source set: final PRD and addendum, final UX DESIGN and EXPERIENCE, and final feature architecture spine. The spec adopts the detailed PRD requirements, UX behavior/design, and architecture spine as companions; it does not replace those authored contracts.
- (capability) CAP-1 — Manage Excel models within the active Structure. Intent: an authorized leader configures, validates and publishes a Structure-specific XLSX/XLSM model. Success: users without permission cannot list or mutate models; authorized users can upload a supported model, see validation, and publish only a valid draft.
- (capability) CAP-2 — Map approved fields and repeated regions. Intent: a configurator associates catalog fields with workbook destinations and repeatable person/Group regions. Success: the model preview identifies missing, duplicate, unauthorized, incompatible and formula-conflicting destinations before publication; only catalog fields are mappable.
- (capability) CAP-3 — Preserve published model versions. Intent: a Structure can publish and replace model versions without changing prior exports. Success: each model has at most one active published version; distinct models may be active together; export confirmation pins the active version used.
- (capability) CAP-4 — Preview and export authorized frequency data. Intent: a leader selects a published model, period and authorized Groups, checks the preview, and receives the corresponding Excel file. Success: generated rows exactly match the protected temporary snapshot shown in the export preview, and unauthorized or changed scope blocks the whole export.
- (capability) CAP-5 — Deliver workbook safely across platforms. Intent: leaders download/share the right XLSX/XLSM result from web, iOS or Android. Success: completion is reported only when the file is available; format/model version are identified; CSV remains usable.
- (capability) CAP-6 — Audit and measure without retaining workbook contents. Intent: operators can trace configuration and export outcomes without collecting spreadsheet rows. Success: history identifies actor, Structure, model/version, filters, result and time; logs/analytics/audit contain no workbook rows, file contents, signed URLs or personal values.
- (constraint) Use the active Structure for every operation and enforce dynamic permission, field and Group scope in the server. Owner bypass never crosses Structure isolation; Group descendants are included only when existing permissions allow.
- (constraint) Provide complete configuration and export capability on web, iOS and Android. Adapt presentation and file transfer to each platform while preserving keyboard/screen-reader access.
- (constraint) Accept .xlsx and .xlsm; output extension matches the model. Preserve formulas and existing embedded VBA without executing macros, external links or workbook connections; request formula recalculation on open, without promising results across spreadsheet readers.
- (constraint) Use a controlled export-field catalog; no arbitrary SQL, user code, macros, or formulas. Do not overwrite formula cells. Repeated-region formula propagation and relative references must be validated against a sanitized workbook fixture.
- (constraint) The export preview and generation use the same exact projected rows through a private, short-lived snapshot. Recheck permissions before consuming and delivering; delete snapshots after terminal processing or expiry. Snapshot bytes never enter queue messages, logs, audit or durable relational history.
- (constraint) The existing CSV export remains available. Use agnostic product terms: Estrutura, Grupo, Evento and person; do not hard-code church/company terminology.
- (constraint) Preserve the architecture spine: React/Expo feature-sliced client; .NET FastEndpoints/CQRS API; asynchronous SQS work items for model validation, draft preview, export preview and generation; private versioned S3 and MySQL metadata; transactional outbox; idempotent workers.
- (constraint) The existing API targets .NET 8; new worker/dispatcher target .NET 10 LTS. Plan the existing API runtime uplift before the .NET 8 support end on 2026-11-10.
- (constraint) Schema changes use idempotent SQL rather than generated EF Core migrations, per project operating preference.
- (non-goal) Executing, creating, modifying or importing VBA/macros; running external workbook connections.
- (non-goal) User-authored SQL, scripts, arbitrary formulas, or spreadsheet automations; calculating formula results in the application.
- (non-goal) Importing workbook edits back into the product, scheduled/email exports, or sharing models across Structures.
- (non-goal) Guaranteeing formula calculation or identical results in every XLSX/XLSM reader.
- (decision) The user confirmed the export-preview snapshot approach: the exact rows displayed in preview are retained temporarily in private S3 for generation, with permission revalidation and cleanup.
- (decision) Prefer an open-source spreadsheet processor and prototype DocumentFormat.OpenXml 3.5.1 first; it is not production-approved until a sanitized .xlsm round-trip proves formulas, VBA and required workbook parts survive.
- (decision) Export entry points are Mais > Configurações da estrutura and Relatórios > Frequência.
- (question) Does the sanitized pilot workbook round-trip correctly with DocumentFormat.OpenXml 3.5.1 while preserving the required formulas, VBA, formatting, hidden sheets and references? If not, which open-license processor passes?
- (question) What upload/output limits, preview snapshot row/byte limits, worker concurrency and snapshot/output retention periods should be set from the leadership pilot?
- (question) What final dynamic permission identifiers, route/API names and platform file picker/share modules should implementation bind to?
- (assumption) The initial field catalog starts with fields in the current frequency report (person, Group, presences, absences, event count, percentage) plus only other existing fields the user is authorized to read.
- (assumption) The stated success thresholds (98% valid generation, 80% autonomous model publication, zero out-of-scope exports) are pilot hypotheses, not committed release gates.
- (assumption) Daniel represents the export leader; the configurator persona/name remains generic and the leadership pilot may refine the flow.
